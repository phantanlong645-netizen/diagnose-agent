# ADR 0003: Structured diagnostic memory and repository orientation

## Status

Accepted; first implementation increment complete

## Context

The current agent uses Eino summarization middleware with a 48,000-token or
48-message trigger. The latest SQLite run showed repeated compactions such as
approximately 49 messages becoming 2 messages, followed by repeated broad
workspace searches. This means the generic summary is acting as the only source
of truth for facts that should survive compaction: exact REST paths, source
files, RPC filters, evidence IDs, errors, and completed checks.

The agent also knows the workflow rules but does not yet have a compact map of
the Access Console modules. When the owning module is unclear it falls back to
`search_files`, `read_file`, or `run_shell`, sometimes scanning generated or
unrelated content. This increases latency and makes the next tool choice less
precise.

This design follows two established patterns:

- OpenAI Agents distinguishes local application context from the conversation
  context actually sent to the LLM. Local state should therefore hold durable
  facts and dependencies rather than relying on replaying every message.
- Letta separates stable memory blocks from archival memory and has addressed
  compaction overflow, runaway compaction, and preservation of structured
  content in its production release notes.

References:

- https://github.com/openai/openai-agents-python/blob/main/docs/context.md
- https://github.com/letta-ai/letta/releases

## Decision

Keep Eino ADK and its summarization middleware as the orchestration layer, but
stop treating a free-form model summary as the sole durable memory. The model
input is composed from four bounded layers:

### 1. Stable global orientation

`internal/agent/engine.go` contains a small, versioned Access Console module
map. It is included in every model instruction and is never generated by the
summary model. It maps a question to the first source to inspect:

- REST contract -> `server/internal/routers/nbi/doc/REST_API_Doc_V0618.md`
- route registration -> `server/internal/routers/nbi/**/routers.go`
- handler/validation -> focused `controlers.go`
- OLT/ONU business logic -> `server/internal/services/{olt,onu}/**`
- device RPC recipes -> `server/internal/pkgs/template_fs/template/olt/**`
- NETCONF transport errors -> `server/internal/pkgs/{netconf,netconf2}/**`
- shared values -> `server/common/{models,constants}/**`
- frontend API/state -> `client/src/{axios,actions,reducers,store}/**`

This is navigation metadata, not a replacement for reading source. The prompt
requires one exact read after the owner is known and forbids full-repository
wildcard scans.

### 2. Pinned diagnostic memory

Add a structured conversation ledger in SQLite. It is injected on every model
call, including after compaction, and is never evicted as ordinary chat text.
Each fact has a stable deduplication key and provenance:

```text
conversation_id
kind: goal | target | route | rpc | source_fact | observed_state |
      error | hypothesis | rejected_hypothesis | completed_check | next_action
key
content_json
status: observed | confirmed | inferred | rejected | open
evidence_ids_json
source_tool
source_locator
confidence
first_seen, last_seen
revision
```

Keep the ledger small by replacing a fact with a newer revision instead of
appending duplicate prose. Facts without evidence may remain `inferred` or
`open`, but must not be promoted to `confirmed` by compaction.

The current diagnostic plan is also structured and pinned:

```text
goal, target, completed_checks[], unresolved_questions[],
next_action, do_not_repeat[]
```

### 3. Recent working context

Retain the current user turn, the latest assistant/tool blocks, and any
in-flight tool-call pair. Project tool observations to summaries plus evidence
IDs; do not put full XML, HTML, logs, or file bodies in every summary request.
Use a target ratio rather than a single hard count:

```text
safe_input_budget = model_context_window
                    - reserved_output_tokens
                    - tool_schema_tokens
                    - safety_margin
trigger when input > 80% of safe_input_budget; the pinned ledger is injected on
every model call, so the extra summary-model request is delayed until the
context is genuinely near its safe limit
compact to 40-50% of safe_input_budget
```

The context window and output reserve must be configurable per model profile.
The current fixed 48,000 threshold is unsafe for providers with a small window
and is therefore removed after the model settings gain these fields.

### 4. Evidence archive

Keep the existing append-only `events` table and `read_evidence` tool as the
source of full raw evidence. Add a lightweight evidence index later so the
agent can retrieve old evidence by ID, tool, route/RPC operation, endpoint,
filename, error text, or keywords instead of repeating the original request.

Raw evidence is never deleted by compaction. The model receives a bounded
summary and a reference; it calls `read_evidence` only when exact content is
needed.

## Compaction pipeline

Compaction is performed in this order:

1. **Deterministic normalization**: remove duplicate system messages, remove
   reasoning-only content, preserve assistant/tool-call pairing, collapse
   duplicate tool results, and replace large observations with evidence
   references.
2. **Pinned-memory injection**: prepend the current ledger and diagnostic plan.
3. **Recent-window selection**: keep the newest complete blocks until the target
   ratio is reached. Never drop the current goal, pinned facts, errors, plan, or
   evidence IDs.
4. **Structured summarization fallback**: only if the deterministic projection
   is still too large, ask the summary model for a strict structured object with
   these sections:

   ```text
   goal
   target
   confirmed_facts[]
   observed_errors[]
   rejected_hypotheses[]
   completed_checks[]
   open_questions[]
   next_action
   do_not_repeat[]
   ```

   Every route, RPC, filename/line, status/error, and evidence ID must be
   preserved exactly when present. The summary model may not invent values or
   credentials.

5. **Validation and atomic checkpoint**: reject a summary missing the goal,
   target, evidence IDs, or next action; retain the prior ledger on failure and
   save the new context plus ledger revision in one SQLite transaction.

Add hysteresis: after a compaction, do not compact again until the context has
grown by a configured amount (for example 25% of the safe budget or eight new
complete blocks). This prevents the repeated 49-to-2 compaction loop observed in
the current database.

## Query and tool deduplication

Before executing a read-only request, normalize a fingerprint consisting of
tool name, method/path or RPC operation/filter, endpoint, workspace path/query,
and relevant arguments. Store the fingerprint with its result evidence ID.

- If the exact fingerprint already succeeded, return the existing evidence
  reference to the model instead of calling the OLT or scanning the workspace.
- If it failed, allow a retry only when the query is materially changed or the
  user explicitly requests a refresh.
- Reject or rewrite broad `search_files` patterns in the tool layer; a prompt
  rule alone is not sufficient because the recent run still issued wildcard
  searches.
- Keep `read_file`, focused `search_files`, read-only NBI, and filtered
  NETCONF calls parallel-capable; serialize writes, shell, and sensitive tools.

## SQLite migration shape

Use a monotonic schema migration in the existing journal implementation:

```sql
CREATE TABLE context_facts (
    conversation_id TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    fact_key TEXT NOT NULL,
    kind TEXT NOT NULL,
    status TEXT NOT NULL,
    content_json BLOB NOT NULL,
    evidence_ids_json BLOB NOT NULL DEFAULT '[]',
    source_tool TEXT NOT NULL DEFAULT '',
    source_locator TEXT NOT NULL DEFAULT '',
    confidence REAL NOT NULL DEFAULT 0,
    first_seen TEXT NOT NULL,
    last_seen TEXT NOT NULL,
    revision INTEGER NOT NULL,
    PRIMARY KEY (conversation_id, fact_key)
);

CREATE TABLE context_plans (
    conversation_id TEXT PRIMARY KEY REFERENCES conversations(id) ON DELETE CASCADE,
    plan_json BLOB NOT NULL,
    revision INTEGER NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE tool_fingerprints (
    conversation_id TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    fingerprint TEXT NOT NULL,
    tool_name TEXT NOT NULL,
    evidence_id TEXT NOT NULL DEFAULT '',
    successful INTEGER NOT NULL,
    last_seen TEXT NOT NULL,
    PRIMARY KEY (conversation_id, fingerprint)
);
```

The first implementation can keep the plan/fact JSON payloads compact while
the keys and indexes remain normalized for deduplication. Do not add a second
agent loop or a second source of truth for raw evidence.

## Implementation order

1. Keep the new repository map in the global instruction (completed in this
   change).
2. Add domain types and SQLite migration for facts, plan, and fingerprints in
   the existing `internal/domain/types.go` and `internal/application/runtime.go`.
3. Add deterministic observation extraction in `internal/agent/engine.go` and
   persist facts after completed tool boundaries.
4. Replace the free-form compaction input with a pinned ledger + recent-window
   projection and a structured-summary validator.
5. Make model context-window/output-reserve settings configurable and expose
   compaction metrics in the event timeline.
6. Add evidence/query deduplication and a focused evidence search only after
   the ledger is working.

## Acceptance criteria

- A confirmed route, exact RPC filter, source path/line, error, and evidence ID
  remain available after at least three compactions.
- The agent does not repeat an identical successful NBI/NETCONF/file search in
  one conversation unless the user requests refresh.
- Compaction output remains below the configured target ratio and cannot loop
  without meaningful context growth.
- A summary-model timeout or malformed summary falls back to the prior ledger
  plus deterministic recent window; the run does not crash or lose context.
- Workspace navigation for a route, handler, service, template, or frontend
  question starts in the mapped owner module rather than a repository-wide
  wildcard scan.
- All visible progress and final answers remain in Simplified Chinese by
  default, while XML/JSON/source identifiers are preserved exactly.
